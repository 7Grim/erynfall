## Primary Format: GLB

**GLB is the one primary runtime format going forward.** This is already policy in `GRAPHICS_STYLE.md` and `CLAUDE.md`. This document makes the technical debt concrete and defines the migration path.

**Why GLB over G3DJ:**
- Native Blender export via File → Export → glTF 2.0
- Carries materials, vertex colors, animations, and node hierarchy in one file
- Industry-standard (used by Unity, Unreal, three.js, etc.) — better tooling
- Loaded via `mgsx-gltf` (already in the dependency tree)
- `validate-models.py` already emits `DEPRECATED` warnings for G3DJ entries

**Why G3DJ is legacy:**
- JSON text format — large files (159 × ~50 KB each = ~7 MB of ASCII)
- Only produced by hand-written Python generators, not Blender-native
- Clip names use non-canonical aliases (`sword`, `spear`) incompatible with the `GRAPHICS_STYLE.md` animation standard
- Requires `getLegacyClipAlias()` shim in the renderer to translate names at runtime

## Technical Debt Register

### 1. Dead G3DB loader in `ModelLibrary.java`
**File:** `client/src/main/java/com/osrs/client/renderer/ModelLibrary.java:453–454`  
**Debt:** `G3dModelLoader g3dbLoader = new G3dModelLoader(new UBJsonReader())` is constructed every `loadModels()` call. Zero `.g3db` files exist anywhere in the repo. The `if (lowerFile.endsWith(".g3db"))` branch at line 474 is unreachable.  
**Fix:** Remove the `g3dbLoader` instantiation and the `.g3db` branch. **Low risk. Done — see cleanup below.**

### 2. Legacy clip alias shim in `Renderer3DExperimental.java`
**File:** `client/src/main/java/com/osrs/client/renderer/Renderer3DExperimental.java` — `getLegacyClipAlias()`  
**Debt:** Translates canonical clip names to old G3DJ names:
```
"attack_slash" → "sword"
"attack_stab"  → "spear"
"run"          → "walk"   // graceful degradation
```
**Why it exists:** G3DJ player/NPC models were authored before the canonical naming standard was defined in `GRAPHICS_STYLE.md`. GLB models use canonical names directly.  
**Fix:** Remove `getLegacyClipAlias()` and its call site once all `actor` models are migrated to GLB with canonical clip names.  
**Blocker:** The 8 player animation G3DJ entries (`player_idle`, `player_walk`, `player_chop`, etc.) and 8 NPC animation entries all use old clip names. These must be migrated before removing this shim.

### 3. Monolithic G3DJ building shells
**Files:** `building_shell_small.g3dj`, `building_shell_service.g3dj`, `building_shell_coastal.g3dj` — on disk, in manifest, in classpath resources.  
**Debt:** These are the old single-GLB building models (no base/roof split). The split GLB variants (`*_base.glb`, `*_roof.glb`) now supersede them. The monolithic entries are unused in `main_world/scene.yaml` (verify before deleting).  
**Fix:** Confirm no `scene.yaml` references, then remove the 3 G3DJ files and their 3 manifest entries.

### 4. `format` field in manifest is not enforced at load time
**File:** `ModelLibrary.java` — the load branch is determined by **file extension** (line 473–502), not by the `format` field in `ModelMeta`. The `format` field appears only in log/error messages.  
**Debt:** Minor inconsistency — a manifest entry could say `format: glb` but have a `.g3dj` filename, and the G3DJ loader would silently be used.  
**Fix:** Add a one-line cross-check in `loadModels()` that logs a warning when `meta.format()` disagrees with the file extension. Low risk, high diagnostic value.

### 5. 159 G3DJ resource files bundled in JAR
**Path:** `client/src/main/resources/models/*.g3dj`  
**Debt:** Maven copies all `*.g3dj` from `art/models/` into the classpath at build time (`pom.xml:copy-model-assets`). These 159 files inflate the packaged client JAR by ~7 MB.  
**Fix:** As each batch of G3DJ models is replaced by GLB, remove the old files from `art/models/`. Maven will stop including them automatically — no pom.xml change needed.

### 6. `G3dModelLoader` import and `JsonReader`/`UBJsonReader` will become unused after migration
**File:** `ModelLibrary.java` imports 3 classes that become dead once G3DJ is fully removed: `G3dModelLoader`, `JsonReader`, `UBJsonReader`.  
**Note:** These imports are still needed until migration is complete. Flag for removal at the end.

## Migration Plan

### Phase 1 — Immediate (no art work needed)

- [x] Remove dead G3DB loader from `ModelLibrary.java` *(done in this task)*
- [ ] Confirm monolithic building shells (`building_shell_small/service/coastal.g3dj`) are not referenced in any `scene.yaml`, then delete them + manifest entries
- [ ] Add format/extension cross-check log warning to `ModelLibrary.loadModels()` *(optional low-risk cleanup)*

### Phase 2 — Actor migration (requires Blender work, highest impact)

Migrate these 8 G3DJ keys to GLB. `player_base.glb` already exists as the base mesh; the animation clips need to be embedded in it (or separate NLA-track GLBs).

| G3DJ key | Status |
|---|---|
| `player_idle` | Needed by all player animation |
| `player_walk` | Needed by movement |
| `player_pickup`, `player_chop`, `player_mine`, `player_fish` | Skilling animations |
| `player_sword`, `player_spear` | Combat animations |

Once all player animation G3DJ keys are removed, `getLegacyClipAlias()` can be deleted.

For NPCs: same pattern — `npc_*_idle`, `npc_*_walk`, `npc_*_action` G3DJ entries get merged into per-NPC GLB files with NLA animation tracks.

### Phase 3 — Props and resources

Rock, tree, furniture, dock G3DJ entries (props + resource category). These have no animations — straightforward GLB replacement. Author in Blender, export, update manifest.

### Phase 4 — Equipment (largest batch, lowest risk)

120+ equipment G3DJ entries. All static (no animation). Bronze GLB equivalents already exist as a template. Migrate tier by tier.

### Phase 5 — Cleanup

Once all G3DJ files are gone:
- Remove `G3dModelLoader` and `G3dj`-specific logic from `ModelLibrary.java`
- Remove `JsonReader`, `UBJsonReader` imports
- Remove `inspect_g3dj()` function from `validate-models.py`
- Remove `g3dj` from the `ALLOWED_FORMATS` set in `validate-models.py`
- Remove `*.g3dj` copy target from `pom.xml`
